## 二、关键发现（按优先级）

### 【P0-1 文档结构失效 · 严重】
- **现象**：仓库根目录**不存在 `docs/` 目录**。README §179 与手册 §1.3 反复引用「唯一文档源 `docs/青禾商城手册.md`」「`docs/archive/`」「`docs/审查报告-20260807.md`」，均为**死链**。
- **后果**：手册自述的「单一文档源 + 历史归档」机制名存实亡；§10.8 引述的 2026-08-07 审查报告经全盘检索**不存在**，P0/P1 结论无从溯源。
- **证据**：`ls docs` → No such file or directory；`find . -iname "*审查*"` → 空；手册实际位于根目录 `青禾商城手册.md`。

### 【P0-2 手册 §10.8「待修复高危项」与代码严重脱节 · 严重】
§10.8 列四项高危，实证逐一核对结果如下：
1. **P0「`/api/pay/callback` 未鉴权可伪造支付成功」** —— 全代码库检索 `callback` 仅命中测试内 `TransactionCallback`，`PayController` 实际仅有 `/create /mockPay /query /wechatNotify /alipayNotify`，**`/callback` 端点已不存在**（证据：`controller/PayController.java` 全文；Grep 零命中业务回调）。**该 P0 实际已缓解，但手册仍标红。**
2. **P1「生产环境 mock 支付可绕过真实支付」** —— `application-prod.properties:20` 已默认 `app.pay.mock-enabled=${PAY_MOCK_ENABLED:false}`，生产默认关闭模拟支付。**已缓解。**
3. **P1「全新库初始化缺 v1.6~v2.0 表/列导致 CI 必挂」** —— `backend/index.sql` 实际 **327 行、14 张表**（已含 `comment/stock_log/coupon/user_coupon/seckill_*/merchant` 全部增量表）；CI（`ci.yml`）仅执行 `index.sql` 后跑 `mvn test`，**不会因缺表挂掉**。**不成立。**
4. **P1「商家保存商品跨 Service 无事务（孤儿商品风险）」** —— 未能复现。`MerchantController.saveProduct`（`MerchantController.java:63`）直接调用 `ProductServiceImpl`（同服务内 `@Transactional`，`ProductServiceImpl.java:152`），核心 `registerMerchant/apply/audit` 亦均 `@Transactional`（`MerchantServiceImpl.java:29/40/94`）。未见跨 Service 写孤儿路径。**疑似已重构或原结论过当。**

> 结论：§10.8 高危清单与代码现状严重脱节，构成「报告失真」风险——比原始缺陷更具误导性（读者会误以为系统存在未修复的支付伪造漏洞）。

### 【P1-1 部署编排硬编码弱口令 · 中高】
- **现象**：`docker-compose.yml` 硬编码 `MYSQL_ROOT_PASSWORD: root123`、`DB_PASSWORD: root123`（行 13/47）。
- **矛盾**：与手册 §7.6 自检建议「不用默认口令、生产关 Druid、改 admin 密码」直接相左；prod profile 的合规（无默认口令）被编排文件抵消。
- **影响**：任何按文档「一键部署」者，数据库直接暴露于弱口令。属生产安全短板。

### 【P1-2 手册数据性错误 · 中】
- §1.3 称 `index.sql`「216 行 9 表」——实际 327 行 14 表（与 §3.1 的 14 表一致，但与 §1.3 自相矛盾）。
- §4.5 #6 记载 `POST /api/pay/callback`「模拟回调（兼容旧接口）」——代码中**不存在**该端点，属 phantom 文档，误导联调。

### 【P2-1 测试无覆盖率门禁 · 中】
- JaCoCo（`pom.xml` 0.8.11）已接入但 **不设门禁**，CI 仅跑测试不卡覆盖率。建议加 `line≥70` 门禁纳入 CI fail。

### 【P2-2 前端「我要开店」入口缺失 · 低】
- 手册 §1.4 自承：后端 `MerchantService.apply` 幂等已就绪，**前端入口待做**。属功能闭环未闭合，但非阻断项。

### 【已核实达标项（正面）】
- **测试数据真实**：后端 9 测试类 / 82 `@Test`（与手册「82 合计」吻合）；前端 3 spec / 20 用例（吻合）。含真实并发集成测试（20 线程抢 5 库存恰 5 单、30 线程抢 10 库存恰 10 单）。
- **CSRF 配置有效**：`application.properties:37` 默认白名单含 `localhost/127.0.0.1` 的 5173/8080，开发态 POST 不被误拦截；`SameSite=Lax` + `HttpOnly` 基础防线到位。
- **CI 真实有效**：`.github/workflows/ci.yml` 起 mysql/redis 服务 → 初始化 `index.sql` → `mvn test` → `package` → 上传 jar；前端 `lint+test+build`。
- **架构纪律良好**：统一 `Result<T>`/`Paging<T>`、全局异常兜底、订单状态机 CAS 守卫、Redisson 分布式锁防超卖、延迟队列关单、令牌桶限流、M6 三方角色 + 归属校验。
- **部署链完整**：Docker Compose 6 服务 + 多阶段 Dockerfile + Nginx SPA 回退 + Prometheus/Grafana provisioning。

## 三、各维度详评

### 功能完整性（92 ✅）
覆盖浏览→购物车→结算→支付→发货→收货→评价→退款/取消/超时关单全链路；M6 平台化（商家入驻/审核/工作台/归属校验）；营销（优惠券规则引擎、秒杀三重防超卖）。未实现项（真实支付凭证、已发货退货退款、货款分账、店铺主页、评价回复、前端开店入口）均已在手册 §9.2/§10 如实披露，**无伪实现**。

### 架构与代码质量（90 ✅）
分层清晰（controller / service(+impl) / dao / xml）。事务纪律到位：`PayServiceImpl`、`OrderServiceImpl`、`CouponServiceImpl`、`ProductServiceImpl`、`MerchantServiceImpl` 关键写操作均 `@Transactional(rollbackFor=Exception.class)`。无桩函数、无模拟降级（支付为「渠道未配置则回退 Mock」的可预期行为，非伪实现）。

### 安全（80 ⚠️）
- 正向：BCrypt 存储、prod 无硬编码口令、`prod` 默认关 Druid、`Cookie.secure=true`(prod)、CSRF 白名单、支付回调签名验签（微信 fail-closed + AES-GCM、支付宝 RSA2）。
- 负向：`docker-compose.yml` 硬编码 `root123`；dev 默认口令 1234 / Druid `druid/druid`（仅本地可接受）；CSRF 基于 Referer/Origin（弱于 token 方案，但学习项目可接受）。

### 测试（85 ⚠️）
数量真实、含并发集成测试，质量可信；唯一短板是无覆盖率门禁，无法防止劣化。

### 文档一致性与可信度（55 ❌）
**最大短板**。死链（`docs/`）、§10.8 失真高危清单、§1.3 数据错误、§4.5 幽灵端点。代码本体优秀，但文档无法如实反映代码，导致「评审失真」——这是比原始缺陷更危险的信号。

### 前端工程化与 UX（88 ✅）
Vue 3 Composition API + Pinia + Vue Router；路由守卫 `requiresAuth/requiresAdmin/requiresMerchant` 鉴权；三态主题（light/dark/system）CSS 变量 30+；Axios 拦截器统一 401/403 处理；Vitest + ESLint 0 error。

### 部署与运维（90 ✅）
`docker-compose.yml` 6 服务 + 4 卷 + healthcheck；多阶段 Dockerfile（maven:3.9-eclipse-temurin-8 构建 → temurin:8-jre 运行）；Nginx SPA 回退 + `/api /uploads` 反代；Prometheus + Grafana 自动 provisioning；CI 真实有效。

### 性能与可扩展性（78 ⚠️）
并发防线（分布式锁、令牌桶、延迟队列、CAS）到位；但缺 Redis 商品缓存、ES 全文检索、MQ 削峰（手册 §9.2 已规划，未实施，属预期范围）。
